# MQTT 协议关键知识点汇总（100条）

> 来源：EMQX MQTT Guide (https://www.emqx.com/zh/mqtt-guide) 及相关教程文章
> 整理时间：2026-08-06

## 一、MQTT 基础概念（1-15）

1. **MQTT 全称**：Message Queuing Telemetry Transport，是一种轻量级、基于发布-订阅模式的消息传输协议，适用于资源受限的设备和低带宽、高延迟或不稳定的网络环境。

2. **MQTT 设计目标**：专为物联网（IoT）场景设计，解决海量设备接入、低带宽、高延迟、网络不稳定等通信挑战。

3. **MQTT 核心特点——轻量级**：协议开销低、报文小，适合处理能力、内存和能耗受限的物联网设备。

4. **MQTT 核心特点——可靠性**：支持多种 QoS 等级、会话感知和持久连接，即使在困难的网络条件下也能保证消息的可靠传递。

5. **MQTT 核心特点——安全通信**：支持传输层安全（TLS/SSL）加密，以及用户名/密码凭证或客户端证书的身份验证和授权机制。

6. **MQTT 核心特点——双向通信**：发布-订阅模式使客户端既可以发布消息也可以订阅消息，实现设备间无缝双向通信，无需直接耦合。

7. **MQTT 核心特点——连续有状态的会话**：支持持久会话，断开连接后 Broker 可缓存未传递的消息，并在客户端重新连接时尝试传递。

8. **MQTT 核心特点——大规模设备支持**：轻量级特性、低带宽消耗和发布-订阅解耦模式使其能够处理大规模物联网部署。

9. **MQTT 版本演进**：MQTT v3.1.1 于 2014 年 10 月发布；MQTT v5.0 于 2019 年 3 月发布，是目前最新规范，向后兼容 v3.1.1。

10. **MQTT 客户端（Client）**：任何运行 MQTT 客户端库的应用或设备都是 MQTT 客户端，如传感器、即时通讯应用、测试工具等。

11. **MQTT Broker（服务端）**：负责处理客户端的连接、断开、订阅、取消订阅等请求，并负责消息的路由和转发。高效 Broker 可应对海量连接和百万级消息吞吐量。

12. **发布-订阅模式（Pub/Sub）**：发送方（发布者）和接收方（订阅者）完全解耦，通过 Broker 完成消息路由，彼此无需知道对方存在。

13. **MQTT 与 TCP 的关系**：MQTT 基于 TCP/IP 协议传输，可选择使用 TLS/SSL 加密实现安全通信。MQTT 协议只要求基础传输层提供有序、可靠的双向字节流。

14. **MQTT 默认端口**：TCP 端口 1883；TLS/SSL 端口 8883；WebSocket 端口 8083；Secure WebSocket 端口 8084。

15. **MQTT 控制报文（Packet）**：MQTT 协议通过交换预定义的控制报文来通信，是 MQTT 数据传输的最小单元。每个报文由固定报头、可变报头和有效载荷三部分组成。

## 二、主题（Topic）与通配符（16-25）

16. **主题（Topic）**：用于标识和区分不同消息，是 MQTT 消息路由的基础。发布者指定消息主题，订阅者订阅感兴趣的主题来接收消息。

17. **主题层级分隔符**：主题通过 `/` 区分层级，类似于 URL 路径，例如 `chat/room/1`、`sensor/10/temperature`。

18. **主题名（Topic Name）**：在发布消息时使用，不允许使用主题通配符。

19. **主题过滤器（Topic Filter）**：在订阅时使用，可以包含主题通配符来同时订阅多个主题。

20. **单层通配符 `+`**：表示匹配任意一个层级，例如 `a/+` 匹配 `a/x` 或 `a/y`，但不匹配 `a/b/c`。

21. **多层通配符 `#`**：表示匹配任意多个层级，必须放在主题过滤器的末尾，例如 `a/#` 匹配 `a/x`、`a/b/c/d` 等。

22. **通配符使用限制**：通配符主题只能用于订阅，不能用于发布。

23. **`$` 开头的主题**：以 `$` 开头的主题必须由服务端决定其使用方式，客户端不能随意使用。例如 `$share` 用于共享订阅，`$SYS` 用于系统消息。

24. **主题别名（Topic Alias）- MQTT 5.0**：允许将主题名映射为双字节整数别名，后续可用别名替换主题名，降低带宽消耗和计算资源浪费。别名映射由双端各自维护，生命周期仅限于当前连接。

25. **主题别名最大值**：通过 CONNECT 和 CONNACK 报文中的属性协商，客户端和服务端分别设置对端可使用的最大主题别名数量。

## 三、QoS 服务质量等级（26-35）

26. **QoS 0 - 最多交付一次**：消息可能丢失，不保证到达。适用于对实时性要求高但可容忍少量丢失的场景，如传感器周期性上报。

27. **QoS 1 - 至少交付一次**：消息保证到达，但可能重复到达。通过 PUBLISH + PUBACK 两次握手实现。

28. **QoS 2 - 只交付一次**：消息保证到达且不会重复。通过 PUBLISH + PUBREC + PUBREL + PUBCOMP 四次握手实现。

29. **QoS 与报文标识符**：QoS 大于 0 的消息需要使用报文标识符（Packet Identifier）在客户端和服务端之间唯一标识消息，以便完成确认流程。

30. **QoS 降级**：如果服务端支持的最大 QoS 小于客户端订阅时请求的最大 QoS，服务端将通过 SUBACK 告知最终授予的 QoS 等级。

31. **QoS 在发布和订阅中的区别**：发布时的 QoS 决定消息从发布者到 Broker 的可靠性；订阅时的 QoS 决定消息从 Broker 到订阅者的可靠性。实际传输 QoS 取两者中的较小值。

32. **QoS 1 消息流程**：客户端发送 PUBLISH → 服务端回复 PUBACK。若未收到 PUBACK，客户端会重发 PUBLISH（DUP 标志置为 1）。

33. **QoS 2 消息流程**：客户端发送 PUBLISH → 服务端回复 PUBREC → 客户端发送 PUBREL → 服务端回复 PUBCOMP。确保消息只被处理一次。

34. **QoS 0 与流量控制**：MQTT 5.0 的流量控制机制（Receive Maximum）仅适用于 QoS 1 和 QoS 2 的消息，QoS 0 消息不受此限制。

35. **QoS 选择建议**：非关键数据用 QoS 0；需要保证到达但可容忍重复用 QoS 1；关键指令且不能重复用 QoS 2。注意 QoS 越高，传输开销越大。

## 四、会话与连接管理（36-48）

36. **MQTT 连接建立**：客户端发送 CONNECT 报文（第一个控制报文），服务端返回 CONNACK 报文告知连接结果。

37. **Client ID**：用于唯一标识客户端连接与会话。MQTT 允许客户端自行指定，也支持由服务端统一分配。

38. **Clean Session（MQTT 3.1.1）**：为 `true` 时创建新会话，断开连接后会话自动销毁；为 `false` 时创建持久会话，断开后会话仍然保持。

39. **Clean Start（MQTT 5.0）**：替代了 Clean Session，为 1 时丢弃已有会话并创建新会话；为 0 时尝试恢复已有会话。

40. **Session Expiry Interval（MQTT 5.0）**：会话过期时间，表示客户端连接断开后会话能在服务端保留多久。设为 0 或缺失时，连接关闭即会话结束；设为 `0xFFFFFFFF` 时会话永不过期。

41. **持久会话的作用**：避免网络中断导致反复订阅的额外开销；避免错过离线期间的消息；确保 QoS 1 和 QoS 2 的消息质量保证不被网络中断影响。

42. **持久会话恢复条件**：必须使用固定的 Client ID 再次连接。如果 Client ID 是动态的，连接成功后将创建新的持久会话。

43. **客户端存储的会话数据**：已发送给服务端但未完成确认的 QoS 1 与 QoS 2 消息；从服务端收到但未完成确认的 QoS 2 消息。

44. **服务端存储的会话数据**：会话是否存在；已发送给客户端但未完成确认的 QoS 1 与 QoS 2 消息；等待传输给客户端的 QoS 0/1/2 消息；遗嘱消息和遗嘱延时间隔。

45. **Keep Alive（保活间隔）**：客户端完成一个控制报文到发送下一个报文之间允许的最大空闲时间。若无其他报文，必须发送 PINGREQ。

46. **Keep Alive 超时断开**：如果服务端在 1.5 倍的 Keep Alive 时间内未收到任何客户端控制报文，将断开连接。

47. **PINGREQ & PINGRESP**：客户端定期发送 PINGREQ 告知服务端自己还活着；服务端响应 PINGRESP 以便客户端判断网络和服务端的活动状态。

48. **Session Present**：服务端通过 CONNACK 中的该字段告知客户端本次连接是之前会话的延续还是全新会话。

## 五、遗嘱消息与保留消息（49-56）

49. **遗嘱消息（Will Message）**：客户端在 CONNECT 报文中设置，若客户端异常断开连接（未发送 DISCONNECT），Broker 会将遗嘱消息转发给其他客户端。

50. **遗嘱消息属性**：和普通消息一样具有主题、QoS、Payload、保留消息标识位等字段。

51. **Will Delay Interval（MQTT 5.0）**：遗嘱消息延迟间隔，用于指示遗嘱消息在连接断开后延迟多久发出。

52. **保留消息（Retained Message）**：除正常转发外，还会保留在 Broker 中。当新订阅创建时，如果存在匹配的保留消息，会立即发送给订阅者。

53. **保留消息存储规则**：Broker 只能为每个主题存储一条最新的保留消息。后续发布的保留消息会覆盖该主题之前的保留消息。

54. **保留消息应用场景**：适用于设备状态、配置信息等需要新订阅者立即获取最新状态的场景。

55. **清除保留消息**：向某主题发布一条空的保留消息（Payload 为空且 Retain 为 true），可清除该主题的保留消息。

56. **遗嘱消息与保留消息结合**：遗嘱消息也可以设置为保留消息，使异常离线状态能被后续订阅者获取。

## 六、MQTT 5.0 新特性（57-78）

57. **MQTT 5.0 设计目标**：在引入大量新特性的同时保持向后兼容 v3.1.1，改善协议的可扩展性和错误处理能力。

58. **原因码（Reason Code）**：MQTT 5.0 扩展了原因码以反映更准确的结果，所有响应报文都支持原因码，用于指示操作结果。

59. **Reason String**：原因码通常是机器易读的，Reason String 承载人类可读的内容，进一步指示操作结果。

60. **用户属性（User Properties）**：MQTT 5.0 允许在除 PING 报文外的所有控制报文中添加自定义的 UTF-8 键值对作为元数据，类似 HTTP Header，提供更好可扩展性。

61. **用户属性传递范围**：用户属性可在客户端与服务端之间传递，也可在客户端与客户端之间传递，取决于具体的控制报文类型。

62. **用户属性应用场景**：传递消息编号、时间戳、文件元数据、区域信息、数据格式、路由信息等，实现应用层级别的消息路由。

63. **Payload Format Indicator**：用于指示消息内容（包括遗嘱消息）是否是 UTF-8 编码的字符串。

64. **Content Type**：用来描述消息的内容类型，可使用 MIME 类型（如 `text/plain`）或自定义字符串，方便接收方处理。

65. **消息过期间隔（Message Expiry Interval）**：允许客户端为消息设置过期时间，避免在服务端停留较长时间的消息仍被转发给订阅端。

66. **共享订阅（Shared Subscription）**：MQTT 5.0 允许将客户端划分为多个订阅组，消息被转发给所有订阅组，但组内客户端以随机、轮询等策略交替接收消息，实现负载均衡。

67. **共享订阅主题格式**：以 `$share/<group-name>/<topic>` 格式订阅，例如 `$share/group1/sensor/temperature`。

68. **共享订阅兼容性**：虽然这是 MQTT 5.0 的特性，但一些 Broker（如 EMQX）也为非 MQTT 5.0 设备提供了共享订阅支持。

69. **订阅选项（Subscription Options）**：MQTT 5.0 提供 4 个订阅选项：QoS、No Local、Retain As Published、Retain Handling。MQTT 3.1.1 仅支持 QoS。

70. **No Local 选项**：用于指示服务端是否可以将应用消息转发给该消息的发布者。通常用于桥接场景。

71. **Retain As Published 选项**：用于指示服务端在向此订阅转发消息时是否保持消息中的 Retain 标志。

72. **Retain Handling 选项**：用于指示当订阅建立时，服务端是否需要向此订阅发送保留消息（0=发送，1=未订阅过才发送，2=不发送）。

73. **订阅标识符（Subscription Identifier）**：客户端在订阅时指定，服务端转发匹配消息时附上关联的订阅标识符，帮助客户端确定消息触发哪个回调。

74. **最大报文大小（Maximum Packet Size）**：MQTT 5.0 允许客户端和服务端各自声明自己愿意接收的最大报文大小，超出限制的报文将被丢弃。

75. **Receive Maximum（接收最大值）**：用于声明双方愿意同时处理的 QoS 1 和 QoS 2 消息的最大数量，实现流量控制。

76. **服务端断开（Server Disconnect）**：MQTT 5.0 允许服务端发出 DISCONNECT 报文，向客户端指示连接被关闭的具体原因。

77. **服务端参考（Server Reference）**：MQTT 5.0 允许服务端通过 CONNACK 或 DISCONNECT 报文指示客户端临时或永久切换至另一台服务端。

78. **请求/响应（Request/Response）**：MQTT 5.0 标准化了请求响应机制，引入响应主题（Response Topic）、关联数据（Correlation Data）和响应信息（Response Information），解决多请求方响应混淆问题。

## 七、安全机制（79-88）

79. **传输层安全 TLS/SSL**：MQTT 支持在传输层使用 TLS 提供端到端安全连接，保护消息免受窃听、篡改或伪造。

80. **单向认证**：仅验证服务器证书，客户端确认服务端身份。能保证通信加密，但不能验证客户端真伪，需结合用户名/密码等认证。

81. **双向认证（mTLS）**：服务端和客户端互相验证证书，双方都需要提供证书，确保通信双方都是受信任的实体。

82. **用户名/密码认证**：MQTT 在 CONNECT 报文中提供可选的 Username 和 Password 字段，支持密码认证和 Token 认证。

83. **增强认证（Enhanced Authentication）- MQTT 5.0**：通过新增的 AUTH 报文实现质询/响应风格的认证，支持 SCRAM、Kerberos 等机制，实现客户端和服务端双向身份确认。

84. **增强认证流程**：客户端发送带认证方法的 CONNECT → 服务端通过 AUTH 报文响应 → 多次交换认证数据 → 最终 CONNACK 返回认证结果。

85. **重新认证**：增强认证完成后，客户端可在任意时间通过 AUTH 报文发起重新认证，无需断开当前连接。

86. **授权（Authorization）**：MQTT 支持对客户端的授权检查，确保只有授权用户才能访问特定主题，进行发布或订阅操作。

87. **TLS 最佳实践**：使用最新版 TLS、强密码套件、可信 CA 证书、证书吊销机制、监控证书过期、安全密钥管理、定期更新补丁。

88. **X.509 证书认证**：客户端在 TLS 握手时呈现客户端证书，Broker 提取 Common Name (CN) 或 SAN 字段作为身份标识，安全性极高。

## 八、流量控制与性能优化（89-94）

89. **流量控制（Flow Control）- MQTT 5.0**：引入 Receive Maximum 属性，允许客户端和服务端根据自己的接收能力约定对方的最大消息发送速率。

90. **发送配额机制**：发送端每发送一个 QoS>0 的 PUBLISH 报文，发送配额减一；每收到一个响应报文（PUBACK/PUBCOMP/PUBREC），配额加一。配额为 0 时停止发送。

91. **流量控制局限**：MQTT 5.0 流量控制仅适用于 QoS 1 和 QoS 2 消息，QoS 0 消息不受此机制约束。

92. **MQTT over QUIC**：EMQX 对 MQTT 的扩展，将传输层从 TCP 替换为 QUIC（基于 UDP），有效减少连接开销和弱网环境下的消息延迟。

93. **QUIC 优势**：0 RTT/1 RTT 快速连接建立、多路复用、连接迁移（网络切换不断连）、端到端加密、改进的拥塞控制，特别适用于车联网等移动场景。

94. **MQTT over QUIC 回退**：若客户端因某种原因未能通过 QUIC 握手，建议自动回退到传统 TCP，避免无法建立通信。

## 九、MQTT-SN 与扩展协议（95-97）

95. **MQTT-SN（MQTT for Sensor Networks）**：专为无线传感器网络（WSN）设计的轻量级协议，与 MQTT 完全兼容发布/订阅模型。

96. **MQTT-SN 特点**：更精简的报文（主题名用 2 字节 Topic ID 取代）、支持休眠模式（设备休眠时消息缓存在服务器）、支持网关发现、遗嘱消息可随时更新。

97. **MQTT-SN 安全局限**：v1.2 连接报文只定义了 Client ID，没有 Username 和 Password，缺乏基于用户名/密码的身份验证，公共网络部署存在安全风险。

## 十、最佳实践与工具（98-100）

98. **MQTTX 客户端**：跨平台的 MQTT 5.0 桌面客户端，支持 macOS、Linux、Windows，提供 Web 端和命令行工具，用于调试和测试 MQTT 连接。

99. **公共 MQTT Broker**：EMQ 提供免费的公共 MQTT 服务器 `broker.emqx.io`（端口 1883/8083/8883/8084），适合学习、测试和原型开发，支持 MQTT 5.0 和 QUIC。

100. **MQTT 开发建议**：发送请求前先订阅响应主题；使用 Client ID 作为响应主题的一部分避免混淆；合理选择 QoS 等级平衡可靠性与性能；敏感场景务必启用 TLS/SSL；利用 MQTT 5.0 主题别名和用户属性提升效率与可扩展性。
